# Security changelog

## Реально сделано в этой ветке

- `db.js`: атомарное изменение баланса через `BEGIN IMMEDIATE`, условный `UPDATE` и проверку `changes === 1`; добавлены таблицы идемпотентности платежей/реферальных выплат.
- `bot.js`: серверный `rIdx` и commit для «Ракетки», HMAC initData с TTL 1 час, доверие `X-Forwarded-For` только при `TRUST_PROXY=1`, CORS по `APP_URL`, отклонение `quest` без серверной проверки.
- `bot.js`: SMS webhook отвергает placeholder/короткий секрет, не принимает сумму только из JSON body и отклоняет неоднозначные pending-заявки; Coinso/Platega/SMS используют идентификатор платежа для защиты от повторов. Platega webhook проверяет RUB и фактическую сумму, если провайдер её прислал.
- `db.js`/`bot.js`: дневной лимит попыток сейфа (20) и растущая цена; код сейфа — ровно 4 цифры, генерация через `crypto.randomInt`; бесплатный кейс списывается условным UPDATE.
- Серверные денежные места в `bot.js` переведены с `Math.random()` на `crypto.randomInt`-based helper.

## Не завершено / требует отдельной работы

- Полная транзакция «processed_payments + баланс + ledger + referral payout» пока не объединена в одну SQLite-транзакцию: текущая защита использует атомарный claim и атомарное изменение баланса раздельно; при сбое между ними нужен recovery/reconciliation.
- Реферальная выплата 15% защищена от повторной выплаты через `referral_payouts`, но полноценная защита от самореферала вторым аккаунтом (платёжные реквизиты/задержка/порог) не реализована.
- Дневные/часовые cooldown-ы hot drop, колеса и streak ещё используют flow с последующим `saveUser`; streak имеет условный UPDATE, hot drop/wheel требуют дальнейшего переноса в DB-операции.
- Атомарный accept duel и полная транзакция списания/settle duel не внедрены.
- Опасные `innerHTML` и клиентские `Math.random()` в `index.html`/`tg_block.js` не были массово переписаны: это отдельный UI/CSP-рефакторинг.
- Turso-схема/`pullFromTurso` не расширена для всех новых таблиц и полностью атомарного payment flow.
- `bets_stats.json` не включался в коммит; существующая история репозитория требует отдельного удаления/ротации, если файл когда-либо содержал чувствительные данные.
