## 3. Экономика: реальные деньги

Проект работает с реальными деньгами. Это определяет ограничения остальных этапов.

- `TOKENS_PER_RUB = 10` (`bot.js`), пополнение: Platega (карта/СБП), Coinso (крипта), Telegram Stars, ручное СБП с подтверждением админа.
- Вывод: `/api/withdraw` (от 200 ₽, нужен депозит).
- Стейкинг 1% в сутки (`STAKE_RATE`), реферальная выплата 15% (`REF_PERCENT`).
- `NON_DEPOSITOR_CAP = 400` токенов: потолок баланса без депозита, проверяется на сервере.
- Игры (`GAMES`-таблица в `bot.js`): ставка 10–100000 токенов, `edge` 0.06–0.065 (преимущество площадки 6–6.5%).

### 3.1 Кейсы (текущая механика)

- Источник: платные кейсы `case_500 … case_10000` (`items.js`, объект `CASES`), стоимость = `cost` токенов; есть также `free_cases` у пользователя (`schema.js`, `users.free_cases`).
- Списание: `playCaseRound()` в `bot.js` требует `bet === c.cost`, иначе отказ; ставка списывается с баланса.
- Шансы: веса `w` в `items.js` (tier cheap 4.0, low 10.5, profit 4.7, high 1.6, jackpot 0.7); выбор через `rollItem(caseId, random01)` с CSPRNG (`rnd01` на `crypto.randomInt`).
- Выигрыш = предмет (`user_inventory`), токены за раунд не начисляются. Ценность забирается продажей (`/api/inventory/sell`, `/sell-all`) по серверной цене.
- RTP кейса: `caseRtp()` (заявлено 0.74–0.88). Фактические значения не пересчитывались.
- Баланс хранится на сервере: `users.tokens`.

Вывод: система кейсов платная и ведёт к выводу средств. По правилам задачи (§2) её не расширяем. Этап 5 (Case Forge) заблокирован до решения владельца.

### 3.2 Апгрейд

- Игры `cases` («Апгрейд кейса», множитель 1.1–30) и `upgrader` («Апгрейдер», 1.1–100) идут через общую игровую таблицу `bot.js`; исход определяет сервер (`/api/play`).
- Есть `user_inventory.upgrade_only` (предметы только для апгрейда).
- Подробности формулы шанса апгрейда (код `playRound`) в этом проходе прочитаны не полностью: «не проверено».
- Апгрейд связан с балансом и стоимостью предметов. Этап 4 (Upgrade Lab) заблокирован до решения владельца: менять финансовые правила без подтверждения нельзя.

## 4. Реальные ошибки и риски (с файлами)

Подтверждено документами репозитория (`CHANGELOG_SECURITY.md`, `README.md`):

| # | Категория | Описание | Файл |
|---|---|---|---|
| A1 | Баланс/безопасность | Цепочка «депозит → баланс → реферальная выплата» не в одной БД-транзакции; используются отдельные атомарные операции и persistent claims | `bot.js` (`creditDeposit`), `db.js` |
| A2 | Безопасность | Нет защиты от самореферала (отпечаток реквизитов/IP/устройства не хранится) | `schema.js` (нет полей), `bot.js` |
| A3 | Безопасность | Нет атомарного endpoint принятия дуэли; есть только `createDuel`, `settleDuel`, `cancelDuel` | `bot.js`, `schema.js` (`pvp_duels`) |
| A4 | Клиентская подмена | В клиенте остаются `Math.random` в денежных сценариях и динамические `innerHTML` (XSS-поверхность) | `index.html` (не проверено построчно) |
| A5 | Тесты | `ui-test.js`, `tg-test.js` устарели и падают на старой вёрстке | `ui-test.js`, `tg-test.js` |
| A6 | Тесты | Полный HTTP smoke с конкурентными вебхуками не запускался | `CHANGELOG_SECURITY.md` |
| A7 | Состояние в памяти | Раунды Револьвера хранятся в `activeRevolvers` (Map) в памяти процесса: при рестарте активный раунд со ставкой теряется (ставка списана, выплаты нет) | `bot.js` (`/api/revolver/*`) |
| A8 | Состояние в памяти | Заказ СБП помечается `paid` в памяти до `await creditDeposit` и откатывается в `pending` при сбое; зависит от кэша `Map`, при рестарте между шагами возможна рассинхронизация | `bot.js` (автоподтверждение СБП) |
| A9 | Секрет по умолчанию | В схеме `vault_safe.secret_code` по умолчанию `'7429'`; если не сменён при инициализации, код сейфа предсказуем | `schema.js` |
| A10 | Хардкод | Цена попытки сейфа `cost = 25` зашита в обработчиках `/api/safe/status` и `/api/safe/guess` | `bot.js` |
| A11 | Утечка данных | `u.notifications` очищается после выдачи клиенту: при обрыве ответа уведомление теряется | `bot.js` |
| A12 | Админ | Админ-проверка: `isAdmin(u)` по `ADMIN_ID`. Админ-отчёты уходят в Telegram по ADMIN_ID. Проверка роли для HTTP-админ-эндпоинтов в этом проходе не найдена: «не проверено» | `bot.js` |
| A13 | Документация | `README.md` описывает «хранилище в памяти (Map)», тогда как реально используется SQLite/Turso; два набора сведений расходятся | `README.md` |
| A14 | Двойная копия фронта | `index.html` и `public/index.html` могут разойтись; защита только `check:frontend` | `tools/sync-frontend.js` |
| A15 | Многоэкземплярность | Rate-limit (`checkRateLimit`) и кэши пользователей в памяти процесса: при нескольких инстансах не работают | `bot.js` |

Положительные находки: CSPRNG для денежных исходов (`rnd01`, `rndInt`), `timingSafeEqual` для секретов (`safeEqualStr`), недоверие к `X-Forwarded-For` без `TRUST_PROXY`, серверный исход игр и цена предметов, идемпотентность по `round_id` (`db.getRound`).

## 5. Риски регрессий для планируемых этапов

- Любая правка `index.html` требует `npm run sync:frontend` (иначе прод и корень разойдутся).

## 6. Уязвимости: сводка по запрошенным категориям

- Клиентская подмена баланса: баланс и исход игр серверные; остаточный риск — клиентский `Math.random` (A4), не проверено.
- Утечка ключей: `.env.example` присутствует, значения по умолчанию для секретов в коде не заявлены; поиск по bundle запланирован на этап 8, пока не выполнялся.
- Проверка прав на сервере: см. A12.
- Двойной клик/повтор: есть идемпотентность по `round_id` и claims платежей; для сейфа и револьвера проверка не выполнялась.
