# Делегирование: как работать параллельно вторым агентом

Задача: два агента (например, Antigravity + этот аудит) правят один проект одновременно и **не мешают друг другу**.

Главный принцип: **делить по радиусу поражения и проверяемости, а не по размеру задачи.**

| Признак | Делегировать | Оставить себе |
|---|---|---|
| Файл | новый или отдельный от моего | тот же, где я правлю |
| Проверка | есть объективный pass/fail (скрипт, grep, PoC) | нужен ручной разбор и суждение |
| Связность | одна функция / один файл | сквозной рефакторинг на 5+ мест |
| Риск | ошибка ловится тестом | ошибка = потеря денег и её не видно |

**Правило одной монеты:** `bot.js` — один владелец в каждый момент времени. Два агента, правящих `bot.js` параллельно, гарантированно получат конфликт в денежной логике, а конфликт в денежной логике — это новый баг. Передача «ключа» — через коммит, не через «я быстро поправлю рядом».

---

## 1. Карта владения файлами

| Файл / область | Кто владеет | Почему |
|---|---|---|
| `bot.js` — денежное ядро (баланс, ledger, игры) | **аудит (я)** | сквозные правки, требуют суждения о деньгах |
| `db.js` — схема, `saveUser`, `atomicBalanceChange` | **аудит (я)** | завязано на инвариант баланса |
| `bot.js` — точечные вставки (см. briefs 3–4) | **Antigravity**, последовательно | изолированы, есть acceptance-тест |
| `public/index.html` + `index.html` (корень) | **Antigravity** | отдельный файл, работаю параллельно с сервером |
| Новые скрипты (`tools/*`, `scripts/*`) | **Antigravity** | нулевой риск конфликта |
| `.env.example`, `README.md` | **Antigravity** | документация, никто не трогает |

> ⚠️ **Ловушка этого проекта:** `index.html` и `public/index.html` — две одинаковые копии.
> В прод (Cloudflare, `wrangler.jsonc` → `assets.directory: "public"`) уходит **`public/index.html`**.
> Правка только корневого `index.html` = фикс не доехал до прода. Всегда правь **оба** и проверяй `diff -q`.

## 2. Контракт — это интерфейс между агентами

Когда два агента работают над клиентом и сервером одной фичи, единственный способ не разойтись —
**заморозить контракт письменно до начала работы.** Контракт пишет тот, кто владеет сервером.

Пример для перехода на серверную авторитетность игр:

```http
POST /api/play
Тело:   { "initData": "...", "game": "dice", "bet": 100 }
Успех:  200 { "ok": true, "mult": 2, "win": 200, "tokens": 1300 }
Отказ:  400 { "error": "Некорректная ставка" | "Недостаточно токенов" }
```
**Клиент не присылает ни `winTokens`, ни `tokens` — вообще. Баланс берёт только из ответа.**

Пока сервер не готов, клиент можно обновить заранее: он перестаёт отправлять `winTokens`
(сервер просто проигнорирует поле) — это безопасно в обе стороны и снимает часть P0-1 сразу.

## 3. Готовые задания для делегирования

Формат: **файл + строки → что сделать → приёмка (команда) → не трогать.**

### Brief 1 — Сверка ledger с балансами ⭐ делать первым

**Почему первым:** пока балансы в БД и журнал расходятся, никто не знает реальный размер ущерба.
Скрипт не меняет данные, только читает. Нулевой риск.

**Файл:** новый, `tools/reconcile-ledger.js`
**Что сделать:** скрипт открывает `data/moneyforup.db` (через `node:sqlite`, как `db.js`) **только на чтение**.

**Главный детектор — разрывы в цепочке ledger.** Баг P0-5 (двойное применение delta) оставлял
в журнале след, который видно только так: у записи `balance_after` не совпадает с `balance_before`
следующей записи того же игрока. Между ними «влезла» правка `saveUser`, которая журнал не писала.

```
для каждого user_id: отсортировать transactions_ledger по id
   ожидаем: ledger[i].balance_after == ledger[i+1].balance_before
   расхождение = величина разрыва в токенах
```
Вывести: `user_id`, id записей, величину разрыва. Отсортировать по величине.

Дополнительно таблицей: `user_id` · баланс в `users` · сумма в ledger · сумма депозитов ·
кол-во заявок на вывод со статусом `paid`.
В конце — итог: сколько токенов в разрывах цепочки и сколько это в рублях (**10 ⬦ = 1 ₽**),
и отдельно — сколько всего токенов на балансах.

**Учесть:** история до появления `db.js` в ledger отсутствует, поэтому у старых аккаунтов
расхождения за тот период не восстановить — отметь это в выводе, чтобы цифры не читались как полные.

**Приёмка:** `node tools/reconcile-ledger.js <путь_к_бд>` завершается с кодом `0` и печатает таблицу.

**СТАТУС: сдано в `4951efe`, проверено на слепке.** Скрипт read-only (`PRAGMA query_only = ON`),
на синтетической базе с двумя начислениями в обход ledger нашёл ровно их (+4 000 ⬦ и +5 900 ⬦)
с указанием пар транзакций — детектор рабочий. Ограничение, о котором надо помнить:
сравнивать `SUM(ledger)` с `users.tokens` напрямую нельзя, стартовые 50 ⬦ регистрации
в журнал не попадают.
Запускать на копии: `cp data/moneyforup.db /tmp/check.db` — против боевой БД не писать ничего.
**Не трогать:** `bot.js`, `db.js`.

### Brief 2 — Клиент перестаёт доверять своему балансу

**Файлы:** `public/index.html` **и** `index.html` (корень) — обе копии, они идентичны
**Что сделать:**
1. Убрать `winTokens` из тела запроса к `/api/record-bet` (и `tokens`, если отправляется).
2. Баланс на экране — **только** из ответа `/api/balance` и из поля `tokens` в ответе игровых запросов.
   Локальный расчёт «было − ставка + выигрыш» для отображения убрать.
3. Не использовать `localStorage` как источник истины по балансу: если там что-то лежит — показывать
   значение из последнего ответа сервера, а не из хранилища.
4. Добавить обработку отказа: сервер вернул `400` → показать ошибку, баланс взять из следующего
   `/api/balance`, **не** откатывать в свою локальную цифру.

**Приёмка:**
```bash
grep -c "winTokens" public/index.html index.html     # ожидается 0 и 0
diff -q index.html public/index.html                 # ожидается «файлы идентичны»
```
**Не трогать:** `bot.js` (серверную часть делаю я — контракт выше).

### Brief 3 — Окно `auth_date` (после того, как я освобожу `bot.js`)

**Файл:** `bot.js`, функция `checkInitData` (~строки 335–336)
**Что сделать:** отклонять подпись, если `auth_date` **в будущем**, и сузить окно:
```js
const age = Date.now() - authDate;
if (!Number.isFinite(authDate) || age < -60_000 || age > 5 * 60 * 1000) return null;
```
**Приёмка:** `node -e` с валидной подписью и `auth_date` из будущего → `checkInitData` возвращает `null`.
Текущий код: `if (!authDate || Date.now() - authDate > 24*3600*1000) return null;` — отрицательный `age` проходит.
**Не трогать:** остальную часть функции (схема HMAC там корректна — не «улучшать» её).

**Файл:** `bot.js`, строки `739`, `957`, `1247`, `1259`, `1516`, `1561`
**Что сделать:** добавить хелпер и обернуть пользовательский ввод, уходящий в `parse_mode: 'HTML'`:
```js
const escHtml = s => String(s ?? '').replace(/[&<>]/g, c => ({ '&': '&amp;', '<': '&lt;', '>': '&gt;' }[c]));
```

Обернуть: `order.details`, `o.details`, `details`, `text` (из SMS-вебхука), `senderPhone`, `method`, `username`.

а не ссылка. Проверить на staging, не на проде.
**Не трогать:** `parse_mode` и тексты сообщений (только обернуть переменные).

## 4. Протокол координации

1. **Один `bot.js` — один владелец.** Передача через коммит: «ключ свободен». Не править параллельно.
2. **Одна задача = один коммит** с говорящим сообщением. Так конфликты разрешаются `git rebase`, а не руками.
3. **Каждая задача несёт приёмку.** Задача без команды проверки — не задача, а пожелание.
   В приёмку всегда входит `node .agents/skills/security-audit/scripts/poc-*.js` — он должен остаться зелёным.
4. **Не «улучшать» соседний код.** Агент, которому дали 6 строк, часто переписывает функцию целиком.
   В брифе всегда есть строка «Не трогать» — она обязательна.
5. **Клиентские файлы правятся оба.** `index.html` и `public/index.html` идут парой, иначе прод не обновится.
6. **После каждой волны фиксов** — прогон `audit.sh` + PoC. Проверяет тот, кто **не** писал фикс.

## 5. Анти-паттерны делегирования

- ❌ Отдать «весь аудит» второму агенту — он найдёт другое и продублирует работу. Делить по файлам, не по теме.
- ❌ Отдать фикс двойной записи баланса как «поправь здесь и здесь»: пять мест связаны, это одна задача с одним решением.
- ❌ Дать задачу без acceptance — нечем проверить, и вы узнаете о регрессии от игроков.
- ❌ Параллельно править `bot.js` вдвоём «в разных местах»: денежная логика связна, конфликт почти неизбежен.
- ❌ Делегировать правку только `index.html` (корень): в прод уходит `public/index.html`.
- ❌ Отдавать задачи, требующие секретов, в чат агента: ключи передаются только через env хостинга.
