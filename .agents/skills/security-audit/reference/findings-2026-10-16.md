## 🔴 P0 — эксплуатируется, деньги теряются сейчас

### [P0-N1] Ракетка: клиент присылает `rIdx`, сервер по нему вычисляет точку краха
**Где:** `bot.js:2172` (приём `rIdx` из тела), `bot.js:2182-2188` (`activeRacketBets.set`),
`bot.js:2208` (`sampleCrash(saved.rIdx)`), `bot.js:372-393` (`sampleCrash` — детерминирован).

**Суть:** `sampleCrash(seedIdx)` — чистая функция от индекса раунда. Индекс раунда
приходит **от клиента** (`rIdx: curRound` в `index.html:4629`), сохраняется без проверки
и позже определяет крах. Атакующий офлайн перебирает индексы, находит такой, где крах
близок к максимуму (~×8.67), ставит и забирает кэшаут с `mult ≤ crash`. Риска нет:
условие `clientMult > serverCrash → взрыв` заведомо не выполняется.

**PoC (живой сервер):**
```
POST /api/racket/bet     { bet: 1000, roundId: "RK_POC_1", rIdx: 7007 }   → 200
POST /api/racket/cashout { roundId: "RK_POC_1", mult: 8.67 }               → win: 8670, mult: 8.67
баланс: 1000 → 8670   (гарантированный +8670 ⬦ = 867 ₽ за раунд, повторяемо)
```
Вывод PoC: `выбран rIdx=7007, предсказанный крах ×8.67 … cashout win:8670`.

**Эффект:** гарантированный вывод кассы. Ставка до 100 000 ⬦ → до ~867 000 ⬦ (86 700 ₽) за раунд,
лимит 60 ставок/мин. Извлекается через `/api/withdraw`.

**Фикс (архитектурный, не «одна строка»):** сервер ОБЯЗАН сам выбирать точку краха и не
принимать её (даже индекс) от клиента. Правильная схема — как в `known-findings.md` R3:
сервер фиксирует крах раунда из CSPRNG до приёма ставок, публикует commit-хэш, а кэшаут
оплачивает `bet × mult`, если `mult < crash` (проверка по СЕРВЕРНОМУ краху, привязанному к
раунду/времени, а не к числу от клиента). Как минимум: `rIdx = Math.floor(Date.now()/ROUND_MS)`
только на сервере и жёсткая привязка ставки к текущему окну времени.

**Проверка:** повторный прогон PoC — кэшаут на «подобранном» крахе должен вернуть отказ.

### [P0-N2] `/api/claim-challenge`: бесконечный кран токенов (type ≠ `streak`)
**Где:** `bot.js:2887-2904`.

**Суть:** у наград за квесты **нет ни кулдауна, ни идемпотентности**. Кулдаун есть только
для `type === 'streak'`. Для любого другого `type` (клиентский `'quest'`) сервер начисляет
`amount` из тела запроса (зажат в 10…250) при каждом вызове. `questId` приходит, но
игнорируется — факт выполнения квеста не проверяется.

**PoC (живой сервер):**
```
POST /api/claim-challenge { type: "quest", amount: 250, questId: "q0" }  ×12 подряд
баланс: 50 → 3050   (+3000 ⬦ без единого выполненного квеста)
```
Вывод PoC: `вызовов: 12, начислено: 3000 ⬦`.

**Эффект:** лимит 20 запросов/мин → до 5000 ⬦ (500 ₽) в минуту с одного аккаунта, без потолка
накопления. Прямая утечка кассы.

**Фикс:** хранить серверный прогресс квестов и выдавать награду ровно один раз на
(пользователь, questId, сутки) — атомарно в БД, как `atomicClaimChannel`/`atomicApplyPromo`.
`amount` никогда не брать от клиента — только из серверной таблицы квестов.

**Проверка:** повторный вызов с тем же `questId` → 400, баланс не растёт.

### [P0-N3] `/api/play` с большим множителем: пол шанса `0.0094` ломает минусовое EV
**Где:** `bot.js:559` (`winChance = Math.min(0.75, Math.max(0.0094, (1-edge)/mult))`),
`bot.js:365` (`safe: maxMult 1000, minBet=maxBet=25`), `bot.js:363` (`scratch: maxMult 200`),
`bot.js:351` (`jumper: maxMult 120`).

**Суть:** формула `winChance = (1−edge)/mult` даёт EV = `−edge×bet` при ЛЮБОМ `mult`. Но
нижняя отсечка `max(0.0094, …)` ломает тождество для игр, где `maxMult > (1−edge)/0.0094`.
Для `safe`: `(1−0.05)/1000 = 0.00095`, отсечка поднимает шанс до `0.0094`, а выплата остаётся
`bet×1000`. EV = `0.0094×25000 − 25 = +210 ⬦` за раунд. Игра для кассы вместо `−5%` даёт `+840%`.

**PoC (живой сервер, 1500 раундов):**
```
POST /api/play { game: "safe", bet: 25, mult: 1000, roundId: "SAFE_E_i" }
раундов 1500, побед 15, выплата 375000 ⬦, сальдо: +337500 ⬦ (100000 → 437500)
```
То же (слабее) для `jumper` (×120, +12.8% EV) и `scratch` (×200, +88% EV) через `/api/play`.

**Фикс:** убрать нижнюю отсечку: `winChance = Math.min(0.75, (1-edge)/mult)` и, при желании,
зажать `maxMult ≤ 0.75/(1−edge)` — тогда тождество `EV = −edge` сохраняется. Либо ограничить
`maxMult` сверху значением `(1-edge)/0.0094`.

**Проверка:** симуляция 10 000 раундов `safe` с `mult=1000` должна давать отрицательное сальдо.

### [P0-N4] Сейф: джекпот 10 000–25 000 ⬦ при цене попытки 25 ⬦ и обратной связи
**Где:** `bot.js:2507-2541` (`/api/safe/guess`), `db.js:981-1050` (`attemptSafeGuess`),
`db.js:194` и `db.js:1025` (джекпот 25 000 → 10 000).

**Суть:** 4-значный код с обратной связью bulls/cows (Mastermind) решается за ~8 попыток
(доказано решателем в PoC), а каждая попытка стоит 25 ⬦. Итог: ~200 ⬦ затрат против джекпота
10 000–25 000 ⬦. `/api/safe/guess` не проверяет потолок бездепозитного игрока и не имеет
внешнего лимита на итог.

**PoC (симуляция точного алгоритма Mastermind):**
```
среднее число попыток: 7.89 (цена 197 ⬦) при джекпоте 10000–25000 ⬦
⇒ +9803 ⬦ за цикл даже при упавшем джекпоте
```

**Фикс:** либо снизить джекпот ниже цены гарантированного решения, либо убрать/ослабить
обратную связь (ограничить число попыток на раунд), либо сделать вывод основной награды
зависимым от числа попыток. Обязательно применить серверный потолок и общий лимит.

**Проверка:** симуляция стратегии на 1000 сейфов → ожидание отрицательное.

### [P0-N5] СМС-вебхук защищён публичным секретом-плейсхолдером
**Где:** `bot.js:1836-1923` (`/api/payment-webhook`), `bot.js:1840-1843` (проверка секрета),
`.env` проекта (`PAYMENT_WEBHOOK_SECRET=your_super_secret_key_here`).

**Суть:** кассовый `.env` использует ровно тот секрет, что лежит в публичном `.env.example`
репозитория. `/api/payment-webhook` по этому секрету зачисляет депозит на ЛЮБУЮ pending-заявку
с подходящей суммой (матчинг **по сумме**, `bot.js:1869-1875`) без реальной оплаты.

**PoC (живой сервер с секретом-плейсхолдером):**
```
POST /api/order-sbp      { rub: 300, termsAcceptedAt: <now> }              → order_id SBP_…
POST /api/payment-webhook{ secret: "your_super_secret_key_here", text: "Пополнение 300р" }
→ matched_order: SBP_…, balance 50 → 3050   (+3000 ⬦ без оплаты)
```

**Эффект:** при выкладке бота с этим значением — бесплатные депозиты (лимит 10/мин).
Извлекается выводом.

**Фикс:**
1. Задать **случайный** `PAYMENT_WEBHOOK_SECRET` в окружении хостинга (и на локальном `.env`);
   убрать плейсхолдер из `.env.example` (оставить пустым, а не рабочим значением).
2. Не матчить заявку по одной лишь сумме: сопоставлять по `order_id`/реквизиту/отправителю.
3. Отклонять запрос, если секрет не задан ЛИБО равен значению из `.env.example`.
4. Ограничить rate-limit по IP, а не по подделываемому `X-Forwarded-For` (см. P2-N1).

**Проверка:** с новым секретом старый плейсхолдер → 403; без совпадения order_id → без зачисления.

## 🟠 P1 — целостность данных и обход правил

### [P1-N1] Дрейф схемы Turso: облако не получает новые колонки → потеря данных при рестарте
**Где:** `tools/init-turso.js:18-107` (схема Turso) против `db.js:215-225` (локальная миграция),
`db.js:379-393` (Turso-`UPDATE` из `saveUser`), `db.js:610-619` (`saveOrder` Turso),
`turso.js:117-127` (pull users), `turso.js:190-200` (pull inventory).

**Суть:** локальная схема мигрирована (`__ensureColumns`) и содержит `rakeback`, `free_cases`,
`free_case_5ref_claimed`, `first_deposit_bonus_claimed` (users), `upgrade_only` (user_inventory),
`bonus` (orders). **Turso-схема их не содержит.** При этом `saveUser` пишет их в Turso,
а `saveOrder` пишет `bonus`. Последствия:

- `saveUser` в Turso падает на «no such column» → `flushQueue` (`turso.js:93-100`) возвращает
  группу в начало очереди и **повторяет вечно**, блокируя синхронизацию всего хвоста. На Render
  (эфемерный диск) облако перестаёт получать балансы/заявки → после деплоя балансы откатываются.
- `pullFromTurso` не переносит `upgrade_only` (и `rakeback`/флаги бонусов). После восстановления
  из облака акционный скин «Cyber-Dagger» теряет `upgrade_only` → его **можно продать** через
  `/api/inventory/sell` за 2400 ⬦ (проверка `bot.js:2303` перестаёт срабатывать). Флаги
  бонусов сбрасываются → повторный `+25%` и повторный кейс за 5 друзей.

**Фикс:** привести `tools/init-turso.js` в соответствие (`ALTER TABLE`/колонки) И добавить те же
колонки в `pullFromTurso` (users: rakeback/free_cases/free_case_5ref_claimed/first_deposit_bonus_claimed;
inventory: upgrade_only; orders: bonus). Добавить проверку на старте, что схемы совпадают.

**Проверка:** `node -e "require('./tools/init-turso.js')"` на копии + pull: скин остаётся
`upgrade_only`, продажа → 400.

### [P1-N2] Cooldown'ы в памяти не персистятся
**Где:** `lastHotDrop`, `lastWheelSpin`, `lastStreakAt`, `channelCheckAt` используются в `bot.js`
(1616, 2828, 2859, 2894, 2626), но **отсутствуют** в схеме/`saveUser`/`getUser` `db.js`.

**Суть:** после каждого рестарта/деплоя кулдауны Hot Drop (1 ч), Колеса (12 ч), стрика (20 ч)
и антиспам проверки подписки обнуляются — их можно забирать заново. На эфемерном хостинге
рестарты частые.

**Фикс:** хранить временные метки в БД (колонки + `__ensureColumns` + запись в `saveUser`).

### [P1-N3] Самоприглашение через второй аккаунт = возврат 15 % депозита
**Где:** `bot.js:245-256` (`setRef`), `bot.js:722-743` (реферальные 15 %).

**Суть:** запрещено только `refId === u.id`. Игрок с двумя аккаунтами привязывает B.ref = A.id
(числовой id проходит через `resolveRef`), и с каждого депозита B аккаунт A получает 15 %
токенами. Депозит 1000 ₽ → 10 000 ⬦ на B + 1 500 ⬦ на A. Возврат 15 % живых денег через вывод.

**Фикс:** квалификация реферала (уникальное устройство/платёжный реквизит), неделя холда
реферальных, ручная проверка всплесков.

## 🟡 P2 — устойчивость, утечки, гигиена

### [P2-N1] Rate-limit вебхуков обходится подделкой `X-Forwarded-For`
**Где:** `bot.js:65-68` (`clientIp`), `bot.js:1784,1804,1837`.

`clientIp` берёт первый `X-Forwarded-For` без доверенного прокси — атакующий меняет заголовок
и получает свежий лимит на каждый запрос. Особенно критично для `/api/payment-webhook`
(10/мин) в связке с P0-N5.

**Фикс:** доверять `XFF` только от известного прокси (nginx), иначе брать `socket.remoteAddress`.

### [P2-N2] `Math.random()` в игровой механике
`bot.js:2375` (Скретч), `2867-2875` (Колесо), `2846` (Hot Drop), `db.js:193`/`1022` (код сейфа).
Для денежных исходов нужен `crypto.randomInt` (в `/api/play` он уже используется).

### [P2-N3] `checkInitData`: окно 24 ч
`bot.js:767`. Replay валидного `initData` в течение суток. Осознанный компромисс (задокументирован),
но снижает порог для любых не-идемпотентных операций; те, что остались (см. P0-N2), надо закрыть.

### [P2-N4] Секреты в истории git (актуально)
`git log -p` по `bot.js` всё ещё содержит боевые ключи Coinso (`66b9…`, `20a0…`) и бывший
дефолт `MUP_SECRET_KEY_2026`. В текущем `.env` ключи Coinso **ротированы** (значения другие) —
это правильно. Требуется зачистка истории + ротация всего, что могло утечь (см. P0-0 в реестре).

### [P2-N5] HTML в сообщениях админу — покрытие неполное
`escHtml` экранирует только `& < >` (без `"`), а данные игрока (реквизиты, комментарии СМС)
уходят в HTML-сообщения. Проверить все новые места (Safe jackpot-уведомление `bot.js:2524`
интерполирует код без `escHtml`, но код — `^\d{4}$`, безопасно).
