# Триаж: как отсеивать находки

Цель — не «найти побольше», а **дать пользователю список, где сверху то, что реально теряет деньги**. Находка без доказательства обесценивает отчёт: пользователь перестаёт верить и закрытым пунктам тоже.

---

## Конвейер из 4 ворот

Каждая гипотеза проходит последовательно. Отвалилась на любых воротах → в «Гипотезы» с явной причиной.

### Ворота 1 — Достижимость
> Есть ли путь от неаутентифицированного (или аутентифицированного как обычный игрок) HTTP-запроса до уязвимой строки?

- Есть ли маршрут, который до неё доходит?
- Не блокирует ли раньше `return send(401, …)`?
- Нужны ли права админа?
- Нужен ли валидный `initData` (то есть Telegram-аккаунт)? Это всё ещё достижимо, но меняет severity.

**Отвал:** код есть, но вызвать нельзя. Не уязвимость.

### Ворота 2 — Контроль входа
> Могу ли я как атакующий записать туда произвольное значение?

- Значение приходит из `body` / query / заголовка?
- Провалидировано ли оно (`Number.isFinite`, диапазон, тип) до использования?
- **Критично:** попадает ли оно в вычисление, которое определяет баланс?

**Отвал:** значение жёстко задано на сервере или уже провалидировано. Не уязвимость.

### Ворота 3 — Ущерб
> Что именно теряется и сколько?

- Реальные деньги выводятся? → P0
- Баланс накручивается, но вывести нельзя? → P1
- Утечка данных пользователей? → P1–P2 в зависимости от объёма
- Спуфинг сообщения админу / сломанная вёрстка? → P2–P3

**Отвал-ловушка:** «атакующий может узнать `userId`» — это не ущерб, `userId` и так приходит в `initData`.

### Ворота 4 — Воспроизводимость
> Работает ли PoC стабильно, здесь и сейчас?

- **Детерминированно** → FIX NOW
- **Гонка / нужен тайминг** → FIX SOON, и честно скажи «воспроизводится не всегда»
- **«Теоретически, если...»** → Гипотеза

## Шкала severity для этого проекта

Меряем **рублями ущерба**, а не абстрактным CVSS. 10 ⬦ = 1 ₽.

| Severity | Критерий | Пример |
|---|---|---|
| 🔴 **P0** | Неавторизованный или обычный игрок получает/выводит деньги напрямую. Потеря масштабируется без ограничений. | Клиент задаёт свой баланс; вебхук без подписи зачисляет депозит |
| 🟠 **P1** | Деньги нельзя получить, но можно обойти правила и создать условия для P0; либо утечка админ-функций | Обход `isAdmin`; двойной claim стейкинга; предсказуемый `orderId` |
| 🟡 **P2** | Ущерб ограничен, нужны особые условия или много шагов | Гонка в зачислении; отсутствие rate limit; утечка лишних полей |
| ⚪ **P3** | Гигиена, без прямого ущерба | Отсутствие `timingSafeEqual`; `auth_date` из будущего; заголовки |

**Правило одного раунда:** пока открыт хотя бы один P0 — не тратить время пользователя на P2/P3. Сначала закрыть кран, потом вытирать пол.

## Калибровка: как отличить настоящую защиту от псевдозащиты

Здесь это — главный навык. В коде есть проверки, которые **выглядят** как защита и создают ложное чувство безопасности. Их обязательно разбирать.

| Псевдозащита | Почему не работает | Что должно быть |
|---|---|---|
| `calcMaxTk = u.tokens - betTk + winTk + 100`, где `winTk` из клиента | потолок считается из клиентского же числа → потолок всегда выше желаемого | сервер сам вычисляет `winTk` |
| `if (nextTk > calcMaxTk && !isAdmin)` | проверяет согласованность с числами клиента, а не с реальностью | сверка с серверным результатом игры |
| `if (nextTk - prevTk > 300 && !body.game)` | наличие `game` отключает проверку | намерение клиента не должно влиять на проверку |
| `if (userDep <= 0 && nextTk > 400)` | потолок исчезает после **одного** минимального депозита | лимит, привязанный к сумме депозита |
| `if (sig && sig !== calcSig)` | отсутствие заголовка = пропуск проверки | `if (!sig \|\| !timingSafeEqual(...)) reject` |
| `process.env.SECRET \|\| 'default'` | репозиторий публичный → дефолт = публичный ключ | падать при старте, если секрет не задан |
| `mid !== PLATEGA_MERCHANT_ID` | обычное `!==`, плюс `merchantId` обычно не секрет | `timingSafeEqual` + подпись/подтверждение через API платёжки |

**Тест на псевдозащиту:** «Если я пришлю результат сам, сколько шагов нужно, чтобы это прошло?» Если ответ ≤ 2 — защиты нет.

## Ложные срабатывания, характерные именно для этого проекта

| Шаблонная «находка» | Почему это не находка здесь |
|---|---|
| «Подделка `initData`» | HMAC-SHA256 на `BOT_TOKEN` — схема корректна. Реально проверяй окно `auth_date` (24 ч — это много для денежных операций) и «время из будущего» |
| «SQL-инъекция» | Базы нет, состояние в `Map()` в памяти |
| «CSRF» | Нет cookie-сессий; аутентификация привязана к Telegram WebApp |
| «Слабый пароль / нет 2FA» | Паролей нет вообще |
| «Отладочный режим в проде» | Проверь, что реально есть `console.log` секретов, а не просто `console.log` вообще |
| «XSS в `index.html`» | Проверяй конкретный путь ввода → рендер. В Telegram WebView последствия ограничены, обычно это P2/P3 |
| «Нет HTTPS» | Telegram Mini App не откроется по HTTP вообще; проверяй конфиг, а не факт |

**Не тащи в отчёт внешний чеклист.** Отчёт должен быть про этот код. Каждая строка — со ссылкой на файл и строку.

## Проверка «а не сломает ли фикс бизнес»

Перед тем как предлагать фикс P0, ответь:
- Не отвалится ли легитимный игрок (например, блокировка всех бездепозитных убьёт воронку)?
- Требует ли фикс ручного вмешательства в прод (например, сбросить подозрительные балансы)?
- Нужна ли миграция данных? (Помни: состояние в памяти — рестарт его обнуляет.)

Пользователь должен понимать **цену** фикса, а не только его наличие.

## Шаблон записи о находке

```markdown
### [P0-1] Клиент задаёт произвольный баланс через /api/sync-balance
Где:        bot.js:1261-1301
Атакующий:  любой игрок с валидным initData, сделавший 1 депозит
Вход:       POST /api/sync-balance  {"initData":"…","tokens":10000000,"game":"dice"}
Условие:    наличие поля "game" отключает проверку скачка баланса
Эффект:     баланс с 3 000 ⬦ → 10 000 000 ⬦ (1 000 000 ₽), далее /api/withdraw
PoC:        scripts/poc-balance-bypass.js  → РАЗДЕЛ 1 (живой сервер), кейсы A/B
Фикс:       tokens приходят только от сервера; /api/sync-balance удалить
Проверка:   повторный запуск PoC должен вернуть исходный баланс
```
