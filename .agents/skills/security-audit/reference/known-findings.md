## ✅ P0-5 — Двойное применение баланса при записи в БД — ИСПРАВЛЕНО

**Статус:** ✅ закрыто (исправлено в рабочей ветке) · подтверждено E2E-тестом на живом сервере

**Что сделано:**
1. `db.js` — из `UPDATE` в `saveUser` убрана колонка `tokens`: функция **физически не может** менять баланс.
   Добавлен детектор рассинхрона: если память и БД разошлись — предупреждение `[Ledger] Рассинхрон` (один раз на игрока) и баланс берётся из БД.
2. `bot.js` — введены `applyBalance()` / `setBalanceTo()`: единственный путь изменения баланса.
   Память синхронизируется из результата `atomicBalanceChange` (БД → память), а не наоборот.
3. Все **5** мест с порядком `SAVE → ATOMIC` переведены на один вызов; заодно закрыты ещё **2** точки,
   которые вообще не сохранялись (`adm_wipe_cheaters`, бонус Hot Drop в боте).
4. Ошибки записи больше не глотаются: `catch (_) {}` вокруг денежных операций заменён на логирование,
   а при неудаче вебхуки отвечают `500`, чтобы провайдер повторил запрос (зачисление не теряется).
5. Исправлена потеря дробных токенов в стейкинге: остаток от `Math.floor` остаётся в `accruedBase`, а не пропадает.

**Проверка:** `node .agents/skills/security-audit/scripts/e2e-exploit-test.js` (поднимает реальный сервер)
```
1) память == БД до атаки                                       ✅
2) эксплойт winTokens=999999 → в БД 1 002 999 (было бы 2 002 998) ✅
3) вывод: списано ровно 2000 ⬦ (было 4000 ⬦)                    ✅
4) отклонение заявки: возврат ровно 2000 ⬦                       ✅
5) стейкинг: списано ровно 500 ⬦, тело вернулось                 ✅
6) детектор рассинхрона за весь тест: 0 срабатываний             ✅
```

**Осталось:** сверить балансы, испорченные этим багом ДО фикса — `tools/reconcile-ledger.js` (Brief 1).
Код-фикс прошлые расхождения не чинит.

<details><summary>Исходное описание бага (для истории)</summary>

Два способа записи баланса использовались вместе, в неверном порядке:

Два способа записи баланса используются вместе, в неверном порядке:
```js
u.tokens = nextTk;                                      // 1335  меняем в памяти
try { db.saveUser(u); } catch (_) {}                    // 1338  ← пишет НОВОЕ значение в БД
try { db.atomicBalanceChange(u.id, delta, …); } catch (_) {}  // 1341  ← прибавляет delta ПОВЕРХ него
```
`atomicBalanceChange()` читает баланс из БД и прибавляет `delta`. Но `saveUser()` уже записал
новое значение — значит `delta` применяется **второй раз**.

**Проверено на реальном `db.js`** (`poc-db-double-write.js`, изолированная копия):
```
Честный раунд (1000 ⬦, ставка 100, выигрыш 200):
     ожидалось 1100 ⬦  →  в БД 1200 ⬦        ❌ +100 ⬦
20 раундов подряд:  ожидалось 2000 ⬦ → 3000 ⬦   ❌ +1000 ⬦
```

**Сломанные места (порядок SAVE → ATOMIC):**

| Строки | Путь | Эффект |
|---|---|---|
| `1338 → 1341` | `/api/record-bet` | выигрыш **×2** в пользу игрока, проигрыш **×2** в минус игроку |
| `1537 → 1538` | `/api/withdraw` | с баланса списывается **двойная** сумма |
| `1456 → 1457` | `/api/claim-channel` | бонус +50 ⬦ начисляется дважды |
| `1480 → 1481` | `/api/claim-cashback` | кэшбэк начисляется дважды |
| `1624 → 1625` | `/api/claim-hotdrop` | выигрыш начисляется дважды |

**Почему это критичнее P0-1:** это происходит **сейчас, без атакующего**, на каждом честном раунде
и каждом выводе. Депозиты и реферальные (порядок ATOMIC → SAVE, строки 284↔293, 303↔310) записываются
корректно — `saveUser` их перезаписывает. Балансы в БД уже расходятся с реальными.

**Почему баг незаметен:** `transactions_ledger` пишет `balance_before` из **уже обновлённой** строки.
Проверено:
```
ledger:      { amount: 100, balance_before: 1100, balance_after: 1200 }
реальный БД: 1200
```
Запись выглядит внутренне согласованной. **По журналу расхождение не видно** — сверка нужна с наружи (Brief 1).

**Эксплойт усиливается:** при `winTokens = 10 000 000` в памяти 10 003 000 ⬦, в БД **20 003 000 ⬦**
(лишний миллион рублей сверх самой накрутки).

**Фикс (не «поправить порядок»):** выбрать **один** источник истины. Правильно — `atomicBalanceChange`
единственный путь изменения баланса, `saveUser` не трогает `tokens` вообще:
```js
// в db.js: убрать tokens из UPDATE — баланс меняется только через atomicBalanceChange
```
Затем в `bot.js` заменить пары на один вызов `atomicBalanceChange(userId, delta, …)` и обновлять
`u.tokens` из возвращённого `balanceAfter`, а не наоборот. Порядок идёт первым в `fix-patterns.md`.

</details>

## 🔴 P0-1 — Клиент задаёт выигрыш в `/api/record-bet` (НЕ закрыт)

**Статус:** 🔴 открыто · `bot.js:1301–1355` (ключевое — `1305`)

```js
let winTk = Math.max(0, Math.floor(Number(body.winTokens) || 0));   // 1305
let nextTk = Math.max(0, Math.floor((u.tokens || 0) - betTk + winTk));  // 1323
```

`calcMaxTk` убран — это была псевдозащита, и её удаление правильно. Но `winTk` **по-прежнему

**PoC (актуальный):** `node .agents/skills/security-audit/scripts/poc-balance-bypass.js`

```
[A] winTokens=999999 при депозите 300 ₽   3000 ⬦ → 1002999 ⬦   ❌ ЭКСПЛОЙТ
[B] sync-balance (установить баланс)      3000 ⬦ → 3000 ⬦      ✅ закрыто (P0-2)
```
