## ✅ P0-5 — Двойное применение баланса при записи в БД — ИСПРАВЛЕНО

**Статус:** ✅ закрыто (исправлено в рабочей ветке) · подтверждено E2E-тестом на живом сервере

**Что сделано:**
1. `db.js` — из `UPDATE` в `saveUser` убрана колонка `tokens`: функция **физически не может** менять баланс.
   Добавлен детектор рассинхрона: если память и БД разошлись — предупреждение `[Ledger] Рассинхрон` (один раз на игрока) и баланс берётся из БД.
2. `bot.js` — введены `applyBalance()` / `setBalanceTo()`: единственный путь изменения баланса.
   Память синхронизируется из результата `atomicBalanceChange` (БД → память), а не наоборот.
3. Все **5** мест с порядком `SAVE → ATOMIC` переведены на один вызов; заодно закрыты ещё **2** точки,
   которые вообще не сохранялись (`adm_wipe_cheaters`, бонус Hot Drop в боте).
4. Ошибки записи больше не глотаются: `catch (_) {}` вокруг денежных операций заменён на логирование,
   а при неудаче вебхуки отвечают `500`, чтобы провайдер повторил запрос (зачисление не теряется).
5. Исправлена потеря дробных токенов в стейкинге: остаток от `Math.floor` остаётся в `accruedBase`, а не пропадает.

**Проверка:** `node .agents/skills/security-audit/scripts/e2e-exploit-test.js` (поднимает реальный сервер)

3) вывод: списано ровно 2000 ⬦ (было 4000 ⬦)                    ✅

<details><summary>Исходное описание бага (для истории)</summary>

Два способа записи баланса использовались вместе, в неверном порядке:

Два способа записи баланса используются вместе, в неверном порядке:
```js
u.tokens = nextTk;                                      // 1335  меняем в памяти
try { db.saveUser(u); } catch (_) {}                    // 1338  ← пишет НОВОЕ значение в БД
try { db.atomicBalanceChange(u.id, delta, …); } catch (_) {}  // 1341  ← прибавляет delta ПОВЕРХ него
```
`atomicBalanceChange()` читает баланс из БД и прибавляет `delta`. Но `saveUser()` уже записал
новое значение — значит `delta` применяется **второй раз**.

**Проверено на реальном `db.js`** (`poc-db-double-write.js`, изолированная копия):
```
Честный раунд (1000 ⬦, ставка 100, выигрыш 200):
     ожидалось 1100 ⬦  →  в БД 1200 ⬦        ❌ +100 ⬦
20 раундов подряд:  ожидалось 2000 ⬦ → 3000 ⬦   ❌ +1000 ⬦
```

**Сломанные места (порядок SAVE → ATOMIC):**

| Строки | Путь | Эффект |
|---|---|---|
| `1338 → 1341` | `/api/record-bet` | выигрыш **×2** в пользу игрока, проигрыш **×2** в минус игроку |
| `1537 → 1538` | `/api/withdraw` | с баланса списывается **двойная** сумма |
| `1456 → 1457` | `/api/claim-channel` | бонус +50 ⬦ начисляется дважды |
| `1480 → 1481` | `/api/claim-cashback` | кэшбэк начисляется дважды |
| `1624 → 1625` | `/api/claim-hotdrop` | выигрыш начисляется дважды |

**Почему это критичнее P0-1:** это происходит **сейчас, без атакующего**, на каждом честном раунде
и каждом выводе. Депозиты и реферальные (порядок ATOMIC → SAVE, строки 284↔293, 303↔310) записываются
корректно — `saveUser` их перезаписывает. Балансы в БД уже расходятся с реальными.

**Почему баг незаметен:** `transactions_ledger` пишет `balance_before` из **уже обновлённой** строки.
Проверено:
```
ledger:      { amount: 100, balance_before: 1100, balance_after: 1200 }
реальный БД: 1200
```
Запись выглядит внутренне согласованной. **По журналу расхождение не видно** — сверка нужна с наружи (Brief 1).

**Эксплойт усиливается:** при `winTokens = 10 000 000` в памяти 10 003 000 ⬦, в БД **20 003 000 ⬦**
(лишний миллион рублей сверх самой накрутки).

**Фикс (не «поправить порядок»):** выбрать **один** источник истины. Правильно — `atomicBalanceChange`
единственный путь изменения баланса, `saveUser` не трогает `tokens` вообще:
```js
// в db.js: убрать tokens из UPDATE — баланс меняется только через atomicBalanceChange
```
Затем в `bot.js` заменить пары на один вызов `atomicBalanceChange(userId, delta, …)` и обновлять
`u.tokens` из возвращённого `balanceAfter`, а не наоборот. Порядок идёт первым в `fix-patterns.md`.

## ✅ P0-1 — Клиент задавал выигрыш в `/api/record-bet` — ИСПРАВЛЕНО

**Статус:** ✅ закрыто (коммит `a07ed28`) · подтверждено двумя тестами на живом сервере

**Что было.** `POST /api/record-bet` принимал `winTokens` от клиента (`bot.js:1305`)
и напрямую формировал баланс. Эксплойт в одну строку в консоли DevTools:
```js
fetch(API_BASE+'/api/record-bet',{method:'POST',headers:{'Content-Type':'application/json'},
  body:JSON.stringify({initData:tg.initData,betTokens:0,winTokens:999999,game:'dice'})})
```
До фикса: 3000 ⬦ → 1 002 999 ⬦ за один запрос (ущерб до 100 000 ₽).

**Что сделано:** исход раунда считает сервер.
- Новый контракт `POST /api/play` (алиас `/api/record-bet`): клиент присылает **только
  выбор** — `{ game, bet, mult, roundId }`. Поля `winTokens`, `tokens`, `win`, `verdict`
  от клиента не читаются вообще.
- CSPRNG (`crypto.randomInt`), `winChance = (1 − edge) / mult`, `win = floor(bet × mult)`.
- Множитель зажимается границами игры (потолок ×20 у dice), ставка — лимитами 10…100000.
- Идемпотентность: повторный `roundId` → `400 «Раунд уже проведён»`, баланс не двигается.
- Неизвестная игра → консервативный профиль (≤ 2× ставки), сервис не падает.
- Потолок бездепозитного игрока (400 ⬦) перенесён на сервер.
- `game_rounds` — каждый раунд записан, инцидент можно расследовать постфактум.
- Клиентская «ловушка проигрыша» (`evalBaitTrap`) удалена: она была подкруткой
  против игрока, которую вскрывали через DevTools.

**Проверка (обе — против реального `bot.js`, прод не трогается):**
```bash
node .agents/skills/security-audit/scripts/e2e-game-authority-test.js   # 18 ✅, exit 0
node .agents/skills/security-audit/scripts/poc-balance-bypass.js        # exit 0: «все векторы закрыты»
```
Второй скрипт раньше был симуляцией старого кода и **всегда** печатал «ЭКСПЛОЙТ» —
теперь он бьёт по живому серверу и выносит вердикт по нему. Раздел 2 того же файла
оставлен как исторический слепок `b8b56f5` — для оценки ущерба.

**Осталось:** сверка уже испорченных балансов — `tools/reconcile-ledger.js`.
Код-фикс прошлые расхождения не чинит.

## ✅ P1-5 — Инвентарь: продажа предметов не обеспечена сервером — ИСПРАВЛЕНО

**Статус:** ✅ закрыто · подтверждено `scripts/e2e-inventory-test.js` (19 ✅, exit 0)

**Что было.** Инвентарь целиком жил в браузере: таблица предметов, жребий, `S.inventory`
и продажа. В `bot.js` и `db.js` слова `inventory` не было вообще. Продажа прибавляла токены
в localStorage; на следующем раунде клиент перезаписывал баланс из ответа сервера — токены
исчезали, а предмет был уже уничтожен. Игрок терял вещь и не получал ничего.

**Что сделано.**

| Слой | Было | Стало |
|---|---|---|
| Каталог (цены, веса) | только в браузере | `items.js` — серверный источник правды |
| Жребий предмета | `Math.random()` в клиенте | CSPRNG на сервере, веса из `items.js` |
| Владение предметом | `S.inventory` в localStorage | таблица `user_inventory` |
| Продажа | `S.balance += price` локально | `POST /api/inventory/sell` → запись в ledger |
| Цена при продаже | из объекта клиента | из БД (куда попала из `items.js`) |
| Журнал | ничего | `game_rounds.item_code` + `item_price` |

**Экономика кейса — принципиальный момент.** Предмет И ЕСТЬ выплата: игрок платит стоимость
кейса, получает предмет, забирает деньги продажей. RTP кейсов 0.74–0.88 (проверяется тестом).
Токены за раунд кейса **не начисляются**: если платить и предметом, и токенами по обычной
формуле, суммарный RTP становится ~1.7 и кейс печатает деньги из воздуха. Это было заложено
в P0-1-фиксе (кейсы уходили в профиль `__default` с ×2) и здесь исправлено.

**Защиты, которые проверяет тест:**
- ставка обязана равняться цене кейса (иначе кейс за 10 000 открывался бы ставкой 10 ⬦, а EV
  предмета — 8 751 ⬦);
- продать можно только свой предмет (чужой id → 404, как и несуществующий — не подсказываем);
- повторная продажа отклоняется (`sold_at IS NULL` в условии UPDATE — защита от двух
  одновременных продаж);
- цена от клиента игнорируется целиком;
- если начисление не прошло, предмет возвращается владельцу, а не исчезает.

**Осталось:** старые локальные инвентари игроков (в localStorage) сервер не увидит — предметы,
выпавшие до этого фикса, остались только в браузерах. Решение продуктовое: либо смириться
(они и так были фантомными), либо разово выдать компенсацию.

## Аудит свежих фич PR #2 (Ракетка 15с, пред-ставки, авто-refresh баланса) — R1…R4

Базовая линия: `4dcb079` (merge PR #2) + правки этой волны. Проверка: `node racket-test.js`

### ✅ R1 — Фантомная ставка: сервер отказал, интерфейс показал «В игре» — ИСПРАВЛЕНО

**Статус:** ✅ закрыто · доказано `racket-test.js` (кейсы 3–4)

`place()` в Ракетке вызывался по клику и его промис нигде не обрабатывался
(`place()` намеренно rethrow-ит, чтобы вызывающий узнал, что раунда не было).
Последствия при отказе сервера (не хватает токенов, лимит запросов):

- `B.inRound=true` выставлялся безусловно → кнопка «ЗАБРАТЬ», статус «В игре»,
  пред-ставка рапортовала «Ставки на новый раунд приняты!» — ставки на сервере нет;
- `Uncaught (in promise) Недостаточно токенов` в консоли;
- кэшаут показывал сумму, которая никогда не начислится.

Локальная проверка `S.balance >= B.bet` — не защита: она сверяется с устаревшим
балансом (в бою он обновляется раз в 5 с), а при двух пред-ставках обе проходят
проверку по ОДНОМУ и тому же старому значению.

**Что сделано:** единый путь `fireBet()` — ставка существует только после ответа
сервера; при отказе интерфейс откатывается (`inRound=false`, `lockedBet=0`) и печатает
причину от сервера. `fireQueued()` срабатывает последовательно (`await`), поэтому вторая
ставка сверяется с балансом ПОСЛЕ первой. У Ракетки появилось поле `B.rnd` — раунд
конкретной ставки (общий слот `window.__round` хранил только последнюю).

### ✅ R2 — «Отмена» ставки возвращала токены только на экране — ИСПРАВЛЕНО

**Статус:** ✅ закрыто · доказано `racket-test.js` (кейсы 1–2)

В окне приёма ставок кнопка «ОТМЕНИТЬ» делала `S.balance += refundAmt` локально и
НИЧЕГО не сообщала серверу, хотя ставка уже была проведена `/api/play` (раунд закрыт
жребием). Токены «возвращались» на экране и исчезали при следующем авто-refresh
(5 с в Ракетке, 20 с в приложении) — со стороны игрока это выглядит как пропажа денег.

**Почему нельзя просто добавить серверный возврат:** клиент узнаёт вердикт раунда
сразу из ответа `/api/play`, поэтому отменяемый раунд = откат проигрыша = бесплатные
деньги (повторяемо, лимит 120 запросов/мин). Возврат ставки на сервере в такой схеме
принципиально небезопасен.

**Что сделано:** клик в окне приёма теперь только СОБИРАЕТ ставку (`B.queued`), на сервер
она уходит на старте полёта. Повторный клик — настоящая отмена: списывать ещё нечего.
Ставка, уже принятая сервером, отмене не подлежит — интерфейс говорит это прямо.

### 🟠 R3 — Кэшаут показывал bet×кэшаут, а сервер платил bet×1.7 — ЧАСТИЧНО (нужно решение)

**Статус:** 🟡 дисплей исправлен, МЕХАНИКА требует решения владельца

`cashBet()` рисовал «забрано ×2.31 → +231 ⬦», считая выплату от множителя кэшаута, а
сервер (после P0-1) закрывает раунд сам: ставка списывается и раунд решается в момент
`/api/play` по `defaultMult` Ракетки (**1.7**, edge 4 %), вердикта клиент не выбирает.
То есть анимация полёта и кэшаут — декорация: реально это бросок с шансом `0.96/1.7 ≈ 56 %`
на `bet × 1.7`. Экран обещал одно, на баланс приходило другое, и авто-refresh это вскрывал.

**Что сделано:** экран показывает фактически начисленное сервером (`B.paid`, `B.rnd`),
а не `bet × кэшаут`; тикер берёт множитель сервера (был ещё и баг разбора подписи:
«Ставка #1 кэшаут ×2.31» → `12.31`, R4).

**Что осталось (решение владельца, код не меняет):** сделать кэшаут настоящим.
Схема, которая сохраняет RTP: сервер выдаёт точку краха раунда (скрытую до раскрытия,
с публикацией commit-хэша), клиент шлёт множитель кэшаута, сервер платит `bet × mult`,
если `mult < crash`. Заметь: `winChance=(1−edge)/mult` при `win=bet×mult` даёт
`EV = −edge×bet` при ЛЮБОМ множителе, поэтому произвольный кэшаут сам по себе
не эксплойт — эксплойтом является только клиентская точка краха (`sampleCrash(seed)`
детерминирован по индексу раунда и вычисляется любым игроком заранее).

### ✅ R4 — Тикер получал склеенный множитель — ИСПРАВЛЕНО

`win()` вылавливал из подписи все цифры подряд: «Ставка #1 кэшаут ×2.31» → `12.31`,
«лунка 3 ×5.0» → `35.0`. Заменено на разбор последнего «×число» (`parseNoteMult`),
плюс приоритет множителя сервера. Проверка: `racket-test.js` (тикер ×1.7, не 11.11).
