## Ключевое изменение: баланс теперь пишется в БД

Раньше состояние жило только в `Map()` в памяти — рестарт обнулял всё. Теперь есть `db.js`,
и **любое изменение баланса идёт через два канала одновременно**:

| Функция | Что делает |
|---|---|
| `db.saveUser(u)` | `UPDATE users SET tokens = <значение из памяти>` — пишет **абсолютное** значение |
| `db.atomicBalanceChange(id, delta, …)` | читает из БД, прибавляет `delta`, пишет ledger — пишет **относительное** изменение |

**Смешивать их в одной операции нельзя.** `saveUser` + `atomicBalanceChange` = delta применяется дважды.
Именно поэтому в аудите есть отдельная проверка (секция `15b`) и PoC `poc-db-double-write.js`.

Правильная целевая модель: `atomicBalanceChange` — **единственный** путь изменения баланса,
`saveUser` не трогает `tokens`.

## Что проверять в `db.js` (новый файл)

- **Порядок вызовов** — главное. См. выше.
- **`PRAGMA` в начале:** `journal_mode = WAL`, `foreign_keys = ON` — учесть, что `db.exec` синхронный.
- **Транзакции не вложены?** `atomicBalanceChange` делает `BEGIN TRANSACTION`; если его вызовут
  изнутри другой транзакции (`atomicApplyPromo`), `BEGIN` внутри `BEGIN` бросит ошибку. Проверь,
  не вызывается ли `atomicBalanceChange` из мест, уже открывших транзакцию.
- **Уникальность:** `promo_activations` защищена `PRIMARY KEY (promo_code, user_id)`.
  У `orders` `id TEXT PRIMARY KEY` — проверь, что `saveOrder` не падает молча на дубликате.
- **`game_rounds` создана, но не используется** — таблица под серверную авторитетность игр уже есть.
  Это фундамент для фикса P0-1: `round_id` как уникальный идентификатор раунда + `status` для
  защиты от двойного расчёта. Используй её, а не создавай новую.
